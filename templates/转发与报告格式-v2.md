# 转发与报告格式 v2

## 给用户的报告

先核验再总结，按以下顺序：

1. **结果与影响**：现在实际完成了什么，对用户有什么影响。
2. **证据**：来源路径/链接、版本/提交/哈希、测试或渲染结果。
3. **状态分栏**：已完成且已验证、已完成待验证、进行中、候选、阻塞/未知。
4. **文件落位**：准确路径、用途、正本关系、打开方式和回滚点。
5. **只有用户能做的**：只列目标/方向/审美/不可逆/发布等保留事项，给选择和后果。

默认使用 Markdown。只有视觉对照或复杂关系必须图示时才输出 HTML。

## Agent → Agent 最小交接（项目内直连，不经统领）

正常项目协作中，两个项目角色之间的交接用下面这个最小块直接传递，统领只维护角色关系和抓冲突，不做日常中转：

> 任务：
> Owner：
> 当前状态：（用宪章 lifecycle 词表：UNKNOWN/DRAFT/EXPLORE/CANDIDATE/APPROVED/FROZEN/DEPRECATED/ARCHIVED）
> 正本：（Git 提交 / Spec / 已批 baseline / 测试的准确路径或版本）
> 本轮产出：
> 下一步交给：

规则：下一个 Agent 必须自行读取「正本」一栏所引的当前文件；本交接块与 Memory、上一个 Agent 的总结只用于导航，不证明项目现状；项目事实不得靠多轮总结接力传递。

## 三条禁止

1. 不预填用户尚未拍板的决定。建议留在引用块外，用户选定后再生成最终转发块。
2. 不代写用户没说过的原话。缺少关键输入时留清楚占位或停止相应动作。
3. 不给裸编号、不让用户拼块。每个编号当句说明含义，交付物必须整块可发送。

## 收到其他 AI 回答时

不要按它的自我评价决定可信度。去实际来源核验，再报告“它声称什么、证据支持什么、哪里仍未知”。AI 可能夸大，也可能自我贬低；两者都不能代替证据。
