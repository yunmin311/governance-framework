# AI 输出文件工程与交付治理手册

**目的：** 让每个 AI 对话在生成文件前知道自己在哪里工作、能读写什么、产物应该放在哪里；完成后让用户不需要在桌面、聊天历史或外部链接中寻找文件。

---

## 1. 核心思想

输出文件不是对话的副产品，而是任务的正式产物。生成文件之前先设计产物边界，生成之后再完成交付、Review、归档和清理。

这不意味着由用户手工为每个对话设计目录。正确分工是：

- AI 检查现有项目并提出结构。
- AI 在授权范围内自行建立必要目录。
- 总管 AI 检查跨对话冲突和正本关系。
- 用户只审批会改变既有结构、长期根目录、正本、删除或重大迁移的事项。

## 2. 为什么不能使用一套固定目录

软件项目、设计库、笔记库、研究项目和外部云文档的产物类型不同。强制建立同一物理目录会制造新的平行结构。

本手册定义逻辑职责和决策流程，不强迫物理目录同名。AI 必须先寻找项目已有的等价位置，再决定是否新建。

## 3. 四种输出策略

### 3.1 原生结构模式 `NATIVE`

适用于已有清晰目录、项目宪章或构建约定的项目。

动作：沿用现有 `src`、`docs`、`design`、`specs`、`tests`、`dist` 或其他目录；只登记本对话的读写范围。禁止再建立一套功能相同的 AI 目录。

### 3.2 对话工作区模式 `DIALOGUE-WORKSPACE`

适用于项目允许 AI 产生中间文件，但不希望混入正式目录的情况。

动作：在项目认可的位置建立以项目、对话或任务编号隔离的工作区。工作区可以包含来源索引、工作稿、Review、回执和临时文件；通过 Gate 的正式产物仍进入项目规定的交付位置。

### 3.3 集中交付模式 `CENTRAL-DELIVERY`

适用于项目只读、产物跨多个项目、平台不能写入项目，或用户已经指定专门输出根目录的情况。

动作：使用经确认的集中根目录，至少按项目和任务隔离；建立链接回原项目的索引。集中目录不能变成无项目归属的文件堆。

### 3.4 外部平台模式 `EXTERNAL-PLATFORM`

适用于网页、Figma、在线文档、云盘或其他只能通过链接交付的产物。

动作：登记标题、平台、稳定链接、权限、生成时间、所属项目、状态和本地索引。能导出时保存可验证快照；不能导出时标记 `EXTERNAL-ONLY` 和访问限制。

只在聊天回复中放一个链接不算完成交付。

## 4. 输出策略选择流程

生成文件前按顺序执行：

1. 解析当前设备、项目实际路径和工作目录。
2. 读取项目宪章、README、AGENTS、CLAUDE、Spec、构建脚本和已有文件结构。
3. 识别已有正本、交付目录、构建产物、临时目录、归档和忽略规则。
4. 检查工具是否能稳定处理中文、空格、路径长度和当前文件系统。
5. 提出两到三个候选策略；列出路径、优点、风险、对既有结构的影响和推荐项。
6. 建立本对话文件范围。
7. 低风险新建任务可在汇报计划后执行；高风险结构变化等待用户批准。

## 5. 逻辑区域

根据项目实际需要映射，不要求全部创建：

```text
manifest        文件落位计划、正本声明、版本和索引
sources         用户提供或实际读取的来源
working         当前任务可修改的中间文件
review          等待评审的候选稿
deliverables    已通过当前 Gate 的交付物
receipts        测试、渲染、差异和验收证据
archive         被替代但仍需保留的历史版本
temporary       可再生且已声明可清理的临时文件
```

已有等价位置时只建立映射，不重复创建。

## 6. 每个对话的文件范围

任何文件型任务都必须建立或复用以下声明：

```yaml
dialogue_id:
project_id:
task_id:
resolved_project_root:
output_strategy: NATIVE | DIALOGUE-WORKSPACE | CENTRAL-DELIVERY | EXTERNAL-PLATFORM
output_root:
read_scope: []
create_scope: []
modify_scope: []
forbidden_scope: []
canonical_outputs: []
temporary_outputs: []
naming_policy:
review_path:
review_owner:
cleanup_policy:
rollback_point:
```

### 6.1 `read_scope`

允许读取的路径或平台范围。读取权限不自动产生修改权限。

### 6.2 `create_scope`

允许新建的目录和文件范围。AI 可以在已授权的新建范围内自行建立必要结构。

### 6.3 `modify_scope`

允许修改的既有文件。必须具体到目录、文件类型或明确文件；不能只写“项目内全部”。

### 6.4 `forbidden_scope`

正本、其他项目、用户私人目录、密钥、未知文件、冻结设计和本任务无关区域。

### 6.5 `canonical_outputs`

本任务完成后被视为正本候选的文件。每类长期事实只能有一个正本；其他格式是发布副本或快照。

### 6.6 `temporary_outputs`

本任务自己创建、可以重新生成、且在开工前声明为临时的内容。未列入这里的文件不能因为“看起来没用”而删除。

## 7. 中文与机器兼容命名

## 7.1 三类名称

- **显示名称**：供用户阅读，可以使用中文。
- **稳定标识**：任务、项目、对话和版本使用短 ID 或 ASCII slug。
- **机器路径**：脚本入口、构建目录、依赖路径和跨平台同步路径优先 ASCII 安全名称。

示例：

```text
显示名称：全域 AI 对话治理手册
稳定标识：governance-handbook-v1
人类文件：个人AI治理-当前批准版.pdf
机器目录：published/governance-handbook-v1/
```

## 7.2 兼容性检查

如果路径含中文、空格、超长名称或特殊符号，AI 应在本任务临时范围内验证创建、读取、覆盖保护、构建和打开。失败时必须报告原因和候选路径；禁止静默改存桌面、下载目录或未知临时目录。

已有中文目录且工具可稳定工作时保持原名，不擅自迁移或英文化。

## 8. Gate F0：生成前文件落位计划

在生成多个文件、长期文件或外部链接前，先输出：

1. 项目实际路径和现有结构证据。
2. 两到三个目录或平台候选。
3. 推荐策略及理由。
4. `output_root` 和文件范围。
5. 计划创建、修改、移动和明确不会删除的内容。
6. `canonical_outputs` 与 `temporary_outputs`。
7. 命名和中文兼容方案。
8. Review、验证、回滚和清理位置。

开工计划必须出现在文件生成之前，不能在任务结束后补写成“本来就这样计划”。

## 9. 何时可以自行执行

满足以下全部条件时，AI 可以在报告计划后直接创建：

- 位于项目或用户已经授权的输出范围。
- 不覆盖同名既有文件。
- 不改变项目长期根结构。
- 不修改其他角色的正本。
- 新目录可被当前项目自然解释。
- 有明确 Review 和回滚方式。

出现以下任一情况必须等待用户批准：

- 在项目外建立新的长期根目录。
- 修改或迁移既有目录结构。
- 覆盖、重命名或移动既有文件。
- 改变唯一正本位置。
- 批量生成可能污染项目的大量文件。
- 清理任务开始前已存在的任何内容。

## 10. Gate F1：文件创建与状态

每个新文件至少登记：任务编号、用途、状态、正本关系、创建者和验证方法。禁止出现多个无版本号的 `final`、`new-final`、`final2`。

推荐状态：

- `WORKING`：当前工作稿。
- `REVIEW`：等待评审。
- `CANDIDATE`：具备候选资格但未批准。
- `APPROVED`：已由有权角色批准。
- `FROZEN`：正式冻结。
- `UNVERIFIED`：没有完成必要验证。
- `QUARANTINED`：事故隔离。
- `DELETE-CANDIDATE`：等待批准的清理候选。

## 11. Gate F2：外部链接交付

外部链接必须登记：

```yaml
title:
platform:
url:
project_id:
task_id:
owner:
access_scope:
created_at:
last_verified_at:
status:
local_index:
export_or_snapshot:
known_limitations: []
```

无法确认访问权限、链接稳定性或内容版本时，状态为 `UNVERIFIED` 或 `EXTERNAL-ONLY`。

## 12. Gate F3：最终文件 Review

任务结束时必须给用户一份最终文件 Review：

1. 最终结论和完成状态。
2. 实际读取、创建、修改、移动的文件。
3. 未执行删除与所有清理候选。
4. 每个交付物的准确路径或稳定链接、用途、状态、版本和打开方式。
5. 唯一正本和发布副本之间的关系。
6. 测试、渲染、截图、哈希或人工检查证据。
7. 未验证项、已知限制和待用户决定事项。
8. 回滚点、恢复方式和下一安全动作。

最终回复不得只说“已经生成”“文件在桌面”或“请打开这个链接看看”。

## 13. Gate F4：清理与归档

### 13.1 可以自行清理

仅限本次任务开始后由当前对话创建、开工前已登记在 `temporary_outputs`、可重新生成且没有被引用的临时文件。清理结果仍需写入最终 Review。

### 13.2 必须请求批准

- 任务开始前已经存在的文件。
- 正本、来源、批准稿、冻结稿、证据、回执和未知用途文件。
- 其他对话创建或仍在引用的文件。
- 任何批量删除。
- 会改变外部链接或历史路径的归档移动。

这些内容只能标记为 `DELETE-CANDIDATE`，并列出路径、理由、替代正本、引用关系和恢复方式。

## 14. Gate F5：仓库与备份

如果项目被定义为长期正式项目，应确认：

- Git 仓库是否存在。
- 远端是否登记。
- 最新正式改动是否提交并推送。
- Obsidian、云盘或发布目录是否只是镜像，不与工程正本分叉。
- 生成物能否从正本重新构建。

本机长期规则：`<项目根路径>` 下的新正式项目必须有 GitHub 远端和可验证推送；可复用 Markdown 同步到 `<Obsidian Vault 路径>`。

## 15. 常见失败

| 失败 | 正确处置 |
|---|---|
| 默认把所有文件放桌面 | 先解析项目和授权输出根目录 |
| 只发一个外部链接 | 登记链接、权限、状态和本地索引 |
| 用户需要自己搜索文件 | 提交最终文件 Review 和准确路径 |
| 每个对话建立自己的平行项目 | 优先沿用原生结构，只隔离工作范围 |
| 中文路径失败后悄悄换位置 | 报告兼容性失败和候选路径 |
| 多个文件都叫 final | 指定唯一正本、版本和状态 |
| 任务结束后批量清理 | 只清本轮预声明临时文件，其余列候选 |
| Obsidian 副本变成另一份正本 | 写明镜像关系，始终从仓库同步 |

## 16. 完成标准

- 对话能解释为什么选择当前输出结构。
- 用户不需要手工设计目录，也不需要自己寻找文件。
- 所有交付物都有准确路径、状态和正本关系。
- 中文与机器路径的选择有兼容性依据。
- 外部链接可追踪，不能访问时会诚实标记。
- 清理范围可审计，不会误删既有内容。
- 长期项目的仓库、远端和知识镜像关系明确。
