# 全量对话盘点、迁移与归档手册

**目标：** 把“电脑里有很多对话”变成一张有证据、有层级、有状态、可治理的地图。  
**原则：** 先盘点，后处置；先迁移价值，后归档；删除必须最后发生。

---

## 1. 盘点范围

第一轮覆盖：

- Claude、Codex、ChatGPT、Gemini、Cursor、Trae、Windsurf 等实际使用过的 AI 对话入口。
- 项目目录中的 `CLAUDE.md`、`AGENTS.md`、Prompt、Spec、规则、记忆和工作流文件。
- 本地 Skill、插件、知识库、Obsidian 笔记和设计资料。
- 与项目状态相关的 Git 提交、任务台账、汇报材料和设计源文件。
- 已归档对话和当前无法打开但仍有索引的对话。

第一轮不要求读完每一条聊天内容。先建立全量目录，再按价值和风险分批深读。

## 2. 四轮盘点法

### 第一轮：发现

只回答“有哪些东西”。

- 列出设备、盘符和主要项目根目录。
- 列出各 AI 平台可见对话。
- 记录对话标题、平台、标识、最后活动时间和可访问性。
- 搜索项目内的治理文件和 Prompt。
- 列出已安装及已归档 Skill。

输出：原始发现清单。不得在这一轮判断删除。

### 第二轮：身份识别

只回答“每个对话实际做什么”。证据顺序：

1. 项目唯一正本中的角色表。
2. 对话自己的系统 Prompt 或固定说明。
3. 对话产生或维护的真实文件。
4. 最近三至五次典型输出。
5. 用户口述。
6. 名称推断。

名称推断只能生成 `UNKNOWN` 候选，不能生成正式职责。

### 第三轮：价值迁移

只回答“什么值得留下”。从对话中提取：

- 已批准决定。
- 当前未完成任务。
- 可复用方法。
- 关键失败和被否决方案。
- 项目事实与路径。
- Prompt 中稳定有效的约束。
- 可形成 Skill 的流程。

迁移完成后记录目标文件和验证人。

### 第四轮：处置

依据证据提出：保留、合并、降级、转为知识档案、归档或删除候选。先让用户批准处置表，再执行任何变更。

## 3. 对话分类

### 核心管理对话

控制项目方向、任务编排、重大决策或统一质量。长期保留，但应避免承担大量具体执行。

### 专业能力对话

具有稳定可复用方法，例如设计拆解、代码评审、学习讲解。保留对话或提炼 Skill，取决于其是否仍需持续上下文。

### 项目执行对话

持续服务特定项目，职责清晰。保留并建立身份卡。

### 知识型对话

价值主要在内容而非角色。先提取为笔记、指南或知识库，然后归档原对话。

### 临时任务对话

完成单一任务。迁移结果后归档。

### 重复对话

职责、来源和输出高度重叠。选择一个主角色，其他迁移差异价值后归档。

### 失效对话

项目、技术、Prompt 或方向已废弃。保留历史证据，停止继续使用。

### 无效对话

没有可靠结果、独立知识或未迁移上下文。可进入删除候选，但仍需留下登记记录。

## 4. 保留评分不是自动裁决

可以按以下维度各评 0–2 分，用于排序而非自动删除：

| 维度 | 0 | 1 | 2 |
|---|---|---|---|
| 当前职责 | 无 | 偶尔 | 核心/持续 |
| 独立知识 | 无 | 部分 | 高价值且独有 |
| 未迁移上下文 | 无 | 少量 | 大量关键内容 |
| 可复用能力 | 无 | 尚未验证 | 已多次验证 |
| 证据质量 | 低 | 混合 | 高且可追溯 |
| 与其他对话重叠 | 完全 | 部分 | 独立 |

高分优先保留，低分优先检查，但最终处置仍由用户批准。

## 5. 对话身份卡填写规则

- `dialogue_id` 必须使用平台可稳定追踪的 ID；没有时生成本地治理 ID。
- `purpose` 用一句话说明存在理由。
- `primary_responsibility` 只能有一个主要职责。
- `out_of_scope` 至少写一项，防止角色无限扩张。
- `required_reading` 只列真正每次必读的正本，避免上下文膨胀。
- `allowed_write_targets` 与 `forbidden_write_targets` 尽量写精确路径或逻辑别名。
- `authority` 分开记录探索、批准、冻结、创建 Skill、删除等权限。
- 所有无法确认字段填 `UNKNOWN`，并附验证动作。

## 6. Prompt 迁移

不要把旧 Prompt 原封不动堆进新 Prompt。采用四步：

1. 切分：角色、工作流、项目事实、输出格式、临时要求。
2. 去重：相同规则只保留一个来源。
3. 归位：跨项目规则进总章；项目规则进项目正本；任务要求进 Spec；稳定方法进 Skill。
4. 验证：用一个真实任务确认新结构没有丢失关键能力。

旧 Prompt 在验证完成前标记 `DEPRECATED-CANDIDATE`，不要立刻删除。

## 7. Skill 迁移

一个对话值得保留，不代表它应完整变成 Skill。提炼 Skill 时只保留：触发条件、输入、必读、稳定步骤、输出、质量检查、失败处理和调用关系。

对话中的具体项目状态、寒暄、一次性决策和被推翻过程应进入项目记录或归档，不进入 Skill 主文件。

## 8. 合并流程

```text
确定主角色
→ 比较两个对话的职责与独有价值
→ 迁移未完成任务
→ 迁移正式决定和可复用方法
→ 更新上下游和身份卡
→ 用真实任务验证主角色能接住工作
→ 将旧对话标记 ARCHIVED
→ 观察一段时间后再决定是否删除
```

## 9. 归档包最低内容

每个重要归档对话至少留下：

- 对话 ID、名称、平台和日期范围。
- 原职责和停止原因。
- 迁移到哪里。
- 关键决定列表。
- 未迁移风险。
- 后继角色。
- 原始导出或访问位置。

## 10. 删除候选安全门

删除前逐项回答：

- 是否还有未迁移的决定、附件、Prompt 或任务？
- 是否存在其他地方没有的知识？
- 是否需要用于事故复盘或证明历史？
- 是否已有可恢复备份？
- 删除目标是否精确，不含通配符或宽泛目录？
- 用户是否明确批准了这个具体目标？

任一答案不确定，停止删除。

## 11. 首次盘点建议节奏

### 阶段一：只建地图

- 确认公司电脑盘符、项目根目录和 AI 平台。
- 列出对话元数据，不深读全部历史。
- 标记当前最重要项目和汇报相关对话为最高优先级。

### 阶段二：恢复最高优先项目的正本链

- 找到项目唯一宪章。
- 找到当前路线图、Spec、决策和设计源。
- 建立现有角色与文件所有权表。
- 把本轮产生的冲突设计隔离。

### 阶段三：设计系统恢复

- 确认最初参考网站分析是否仍存在。
- 确认冻结设计版本和实现版本。
- 建立设计中枢/执行/辅助的真实职责候选，等待用户确认。

### 阶段四：全域剩余项目

- 按项目重要性批量登记学习、网络、笔记和其他设计项目。
- 只对高价值或高风险对话做深读。

## 12. 首轮盘点完成报告格式

首轮报告不得声称“所有对话已经完全理解”，除非确实逐一读取并记录证据。建议使用以下格式：

```text
一、发现范围与不可访问范围
二、项目总数与优先级
三、对话总数与分类
四、每个项目的唯一正本
五、确认的角色关系
六、冲突与未知项
七、冻结内容与禁止改动
八、Prompt/Skill 重复与缺口
九、保留/合并/归档/删除候选
十、需要用户决定的最小清单
十一、建议的第二轮治理顺序
```
