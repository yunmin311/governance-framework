# 跨领域可复用的工程治理思维

**本章回答：** 这套宪章、纠偏、文件 Gate 和最终 Review 背后到底是什么思维？以后换到开发、设计、研究、笔记或写作时，应该搜索什么、复用什么？

---

## 1. 给它一个总名

本治理包把这套综合方法命名为：

> **可追溯的产物生命周期治理**  
> **Traceable Artifact Lifecycle Governance**

这是为了便于理解和复用而提出的综合名称，不是一个既有国际标准、注册方法或单一学派。

它关心的不是“文件是否整齐”，而是：

- 产物属于哪个上下文。
- 谁根据什么来源生成。
- 当前可信基线是什么。
- 允许谁在什么范围内改变。
- 什么时候可以称为完成。
- 如何交付、Review、变更、回滚、归档和清理。

## 2. `Artifact` 应该怎么翻译

`Artifact` 在不同领域有不同常用译法：

| 领域 | 常用中文 | 例子 |
|---|---|---|
| 软件工程 | 制品、构建产物 | 安装包、容器镜像、测试报告 |
| 设计 | 设计产物、交付物 | 原型、设计稿、Token、组件库 |
| 项目管理 | 项目产物、工作产品 | 计划、决策记录、验收材料 |
| 研究 | 研究产物 | 数据、分析代码、论文、图表 |
| 知识管理 | 知识产物 | 笔记、索引、卡片、知识图谱 |
| 档案管理 | 记录、档案 | 正式文件、证据、处置记录 |

本治理包在面向用户时优先写“产物”或“交付物”，在软件构建语境中可以写“制品”。不要为了术语统一而忽略领域习惯。

## 3. 配置管理：控制系统如何变化

### 中英文

- Configuration Management：配置管理
- Configuration Item：配置项
- Configuration Baseline：配置基线
- Change Control：变更控制
- Configuration Audit：配置审计

### 思想

先识别哪些东西值得受控，再建立当前批准快照；后续改变通过明确流程发生，而不是每个执行者自行覆盖。

NASA 的系统工程手册把配置识别、变更控制、状态记录和配置审计组织成一套跨生命周期流程；SEBoK 也强调基线是管理、控制和评价后续变化的正式参考点。[NASA Systems Engineering Handbook](https://www.nasa.gov/wp-content/uploads/2018/09/nasa_systems_engineering_handbook_0.pdf)、[SEBoK Configuration Management](https://sebokwiki.org/wiki/Configuration_Management)

### 在本系统中的表现

- 一个项目正本。
- 设计冻结和版本号。
- 新方案先是 `EXPLORE/CANDIDATE`。
- 修改冻结内容需要变更请求。
- 保留回滚点和审计记录。

### 可用于

代码版本、品牌规范、报告数字、课程笔记、研究数据和写作大纲。

## 4. 来源追踪：知道结果从哪里来

### 中英文

- Provenance：来源、溯源、来源追踪
- Traceability：可追溯性
- Data Lineage：数据血缘，通常更偏数据流
- Chain of Custody：保管链，常用于证据和合规

### 思想

一个结论的可信度不仅取决于内容看起来是否合理，还取决于产生它的实体、活动和角色是否可追踪。W3C PROV 用 `Entity / Activity / Agent` 描述来源关系，并把来源信息用于评估质量、可靠性和可信度。[W3C PROV Overview](https://www.w3.org/TR/prov-overview/)

### 在本系统中的表现

- AI 列出实际读取文件。
- 设计稿标注基线版本和参考来源。
- 外部链接登记平台、权限和验证时间。
- 发布物可以追溯到 Markdown 正本和构建过程。

### 可用于

事实核查、研究引用、AI 内容生成、数据分析、决策记录和合规审计。

## 5. 限界上下文：让每个角色只在自己的世界里正确

### 中英文

- Bounded Context：限界上下文、边界上下文
- Context Map：上下文映射
- Ubiquitous Language：通用语言、统一语言
- Separation of Concerns：关注点分离

### 思想

大型系统很难依靠一个统一模型覆盖所有事情。领域驱动设计通过限界上下文建立内部一致的模型，并显式描述不同上下文之间的关系。Martin Fowler 将其概括为 DDD 战略设计的核心模式。[Martin Fowler: Bounded Context](https://martinfowler.com/bliki/BoundedContext.html)

### 在本系统中的表现

- 每个项目有自己的宪章和词汇。
- 每个对话有身份卡、文件范围和上下游。
- 总管负责连接和冲突，不代替专业角色。
- 设计、实现、顾问和笔记不能互相偷换批准权。

### 可用于

多团队协作、微服务、品牌子系统、课程体系、知识库分区和多客户项目。

## 6. 阶段与门禁：到达标准后再继续

### 中英文

- Stage-Gate：阶段—门禁、阶段关卡
- Quality Gate：质量门禁、质量关卡
- Review Gate：评审门
- Go / Kill / Hold / Recycle：继续 / 终止 / 暂停 / 返工

### 思想

把复杂过程拆成工作阶段和决策点。Stage-Gate 的 Gate 会检查前一阶段交付物、预设标准和下一阶段决定，而不是等所有工作结束后才发现基础错误。[Stage-Gate Discovery-to-Launch](https://www.stage-gate.com/about/stage-gate-innovation-performance-framework/discovery-to-launch-process/)

### 在本系统中的表现

- 生成 HTML 前先过开工与骨架 Gate。
- 设计基线没有读取就不进入实现。
- 没有渲染证据就保持 `UNVERIFIED`。
- 文件位置和 Review 不清楚就不算交付。

### 可用于

产品开发、设计评审、论文写作、采购决策、内容发布和活动筹备。

## 7. 完成定义：把“差不多”变成共同标准

### 中英文

- Definition of Done：完成定义
- Acceptance Criteria：验收标准
- Ready：就绪
- Increment：增量

### 思想

完成不是执行者的感觉，而是共享的质量状态。Scrum Guide 把 Definition of Done 描述为增量达到产品质量措施时的正式状态；未满足就不能视为完成。[The 2020 Scrum Guide](https://scrumguides.org/scrum-guide.html)

### 在本系统中的表现

- HTML 必须同时通过内容、结构、视觉、来源和文件 Gate。
- 代码完成不能替代视觉批准。
- 自检不能替代用户最终决策。
- “生成了文件”不能替代最终文件 Review。

### 可用于

几乎所有协作任务。它尤其适合解决“每个人对完成理解不同”的问题。

## 8. 可复现性：不要依赖某个对话的记忆

### 中英文

- Reproducibility：可复现性
- Reproducible Build：可复现构建
- Deterministic Build：确定性构建
- Independent Verification：独立验证

### 思想

给定同样的来源、环境和说明，其他人能够重新生成并比较结果。Reproducible Builds 项目强调从源到二进制建立可独立验证的路径，同时记录构建环境和比较方法。[Reproducible Builds](https://reproducible-builds.org/)

### 在本系统中的表现

- Markdown 是正本，DOCX/PDF 可以重建。
- 设计记录 Token、组件、源文件和渲染方式。
- 发布包记录哈希、页数和验证结果。
- 新对话读取文件即可恢复，不依赖旧对话记忆。

### 可用于

软件构建、数据分析、设计系统、文档出版、实验和自动化报告。

## 9. 记录生命周期：文件也有出生、使用和退出

### 中英文

- Records Lifecycle：记录生命周期
- File Plan：文件计划
- Retention：保留
- Disposition：处置
- Records Schedule：记录保留与处置计划

### 思想

文件不是永远堆积，也不是任务结束就随手删除。需要区分创建、使用、评审、发布、保留、归档和处置。美国国家档案馆将 File Plan 作为面向具体办公室或项目的简明管理工具，并要求位置、责任和处置说明可执行。[U.S. National Archives: File Plans](https://www.archives.gov/records-mgmt/scheduling/implementation)

### 在本系统中的表现

- 生成前文件落位计划。
- 工作稿、候选稿、正本和归档分状态管理。
- 临时文件预先声明。
- 既有文件只能列为 `DELETE-CANDIDATE`，等待批准。

### 可用于

个人文件管理、公司知识库、项目资料、研究数据、合同和创意素材。

## 10. 设计系统：一致不是复制，而是连续

### 中英文

- Design System：设计系统
- Design Tokens：设计 Token、设计变量
- Component Library：组件库
- DesignOps：设计运营、设计运作
- Continuity：连续性

### 思想

共享原则、Token、组件和验证方式，使产品跨页面、平台和时间保持连续。美国政府 Web 设计系统强调 continuity，同时指出一致并不等于所有服务完全同形；应先寻找现有指南和共享解决方案。[USWDS Design Principles](https://designsystem.digital.gov/design-principles/)

### 在本系统中的表现

- 首屏和尾部使用同一套 Token 与组件语言。
- 新探索和沿用规则分开。
- 设计基线比模糊风格描述更重要。
- 评审完整页面，不只看精选截图。

### 可用于

网页、品牌、演示文稿、数据可视化、文档模板和内容风格。

## 11. 人在回路：AI 能做很多，但不能成为所有权力的来源

### 中英文

- Human-in-the-Loop：人在回路
- Human Oversight：人工监督
- AI Governance：AI 治理
- Accountability：问责、责任归属
- Continuous Monitoring：持续监测

### 思想

治理贯穿 AI 生命周期，角色、责任、测试、文档和事件处理必须持续存在。NIST AI RMF 要求明确人机配置中的职责和监督，并强调文档、测试、事件识别和持续治理。[NIST AI RMF Core](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)

### 在本系统中的表现

- AI 可以发现、规划、执行、验证和建议。
- 用户保留删除、重大改向、最终批准和解除冻结权。
- AI 必须承认无法访问和无法验证的范围。
- 事故模式会暂停自动推进。

### 可用于

所有高影响 AI 使用场景，包括设计决策、代码变更、财务分析、公开内容和知识治理。

## 12. 一套跨领域循环

```text
Context      先明确项目、角色和边界
Source       找到来源、证据和唯一正本
Baseline     建立当前可信基线
Plan         规划产物、文件范围和验证方式
Produce      在授权范围内生成
Gate         用预先定义的标准检查
Review       让适当角色和用户评审
Release      发布并登记正本、版本和打开方式
Archive      归档被替代版本
Dispose      对清理候选做有批准的处置
Learn        把事故和反馈变成下一版规则
```

这套循环不是瀑布流程。小任务可以几分钟走完一圈，大项目可以让每个阶段都独立成循环。

## 13. 五个跨领域例子

### 13.1 软件开发

边界是仓库与模块；正本是代码和 Spec；基线是提交；Gate 是测试、构建和 Review；交付物是发布制品；回滚点是提交或版本标签。

### 13.2 设计

边界是品牌、页面和组件；正本是设计源与 Token；基线是已批准艺术方向；Gate 是逐页面、逐断点视觉验收；交付物是源文件、实现和发布截图。

### 13.3 研究

边界是研究问题和数据许可；正本是原始数据、分析脚本和方法；基线是冻结数据集或实验版本；Gate 是可复现分析、同行 Review 和引用检查。

### 13.4 笔记与学习

边界是课程、主题或知识域；正本是来源明确的笔记；基线是当前知识结构；Gate 是出处、链接、重复和可检索性；归档过时理解但不把它冒充当前结论。

### 13.5 写作与内容

边界是读者、主题和发布渠道；正本是主稿；基线是已确认大纲与事实库；Gate 是事实、结构、语气、版权和发布格式；发布副本不能独立改写事实。

## 14. 什么时候不要把流程做重

这套思想的目标是降低风险，不是制造表格。

- 一次性低风险任务可以使用一页任务包和一份最终 Review。
- 只读问答不需要新建完整目录。
- 只有一个小文件时不必创建七层结构。
- 风险越高、参与角色越多、生命周期越长，治理强度才应越高。
- 能自动验证的规则优先自动化；真正需要判断的部分才进入人工 Gate。

## 17. 最简记忆法

以后遇到任何领域，只问十个问题：

1. 我现在在哪个上下文？
2. 谁负责，谁批准？
3. 正本和来源在哪里？
4. 当前可信基线是什么？
5. 允许改变什么？
6. 产物放在哪里？
7. 什么条件才算完成？
8. 谁做 Review？
9. 出错如何回滚？
10. 哪些保留、归档或等待批准后清理？

这十个问题回答清楚，开发、设计、研究和知识工作都会稳定很多。
